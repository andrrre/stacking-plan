# Make room Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When no space fits a requirement, propose up to three one-tenant moves that create a fit, preview a move on the 3D building, and apply it as a scenario.

**Architecture:** A pure solver (`makeRoom`) reuses `findFits` and `applyScenario`, so every option it returns is already proven to apply and to produce the freed block as a match. A preview is one unsaved field in app state; while it is set, the stack model is built from the building with the move applied and the freed block as the only match, so the 2D stack and the 3D building show the same end state. The 3D scene adds one flying block on top of that end state.

**Tech Stack:** TypeScript, React 19, zod 4, three.js 0.187 with `@react-three/fiber` 9, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-16-make-room-design.md`

## Global Constraints

- Immutable code only: never mutate buildings, suites, leases or state.
- Tests first: every task writes the failing test before the code.
- Functions under 50 lines, files under 800 lines, no `console.log`, no hard-coded values outside `constants.ts` or a named constant.
- No new dependencies. No network. No AI.
- Existing hero-building figures and existing tests must not change.
- The 3D building is the primary surface; the 2D stack must show the same state.
- A preview never changes `state.changes` or the base building.
- Wording never presents a move as agreed.
- Commit messages: `<type>: <description>`, types feat, fix, refactor, docs, test, chore.
- Another session has uncommitted work in this checkout (`src/features/three-d/scene/CameraRig.tsx`, `src/features/three-d/zz-probe.test.ts`). Work in a git worktree on branch `feature/make-room` and stage only the files each task names.

## Review Focus

1. No vacant suite is big enough for any blocking tenant: the Make room section is absent, not empty. (Task 1, Task 3)
2. The date slider is on a future date: an applied move still yields a firm fit on that date, not a potential one. (Task 1)
3. The blocking tenant has an open-ended lease, or its lease starts on the date shown: it is not offered. (Task 1)
4. A preview is showing and the broker changes the requirement, the date or the building, or resets the scenario: the preview ends. (Task 2)
5. Show move is pressed in floor view, in the 2D stack, or with reduced motion: the end state shows, with no flight and no error. (Task 2, Task 4, Task 5)

Fixture tests, one `it` each, on a one-floor building `[A vacant 5,000 J] [B leased 2,000 –]` plus a second floor holding the destination, requirement 6,000 SF:

- `'returns [] when a fit already exists'`: requirement 4,000 → `[]`.
- `'returns [] when no vacant suite is at least the mover's size'`: destination 1,500 SF → `[]`.
- `'never uses a potential or committed suite as the destination'`: destination with a lease ending between today and D (not vacating), and one with a future lease → `[]`.
- `'never uses a suite of the freed block as the destination'`: only vacant suites are A and a 2,500 SF suite joined into the freed run → `[]`.
- `'skips a mover with an open-ended lease'`: B's lease `end: null` → `[]`.
- `'skips a mover whose lease starts on D'`: B's lease `start: D` → `[]`.
- `'respects maxSf and maxRentPsf on the freed block'`: `maxSf: 6_500` → `[]`; asking rents blending above `maxRentPsf` → `[]`.
- `'picks the smallest destination that fits, ties to the higher floor'`: destinations 2,000 SF on floors 2 and 3 and 3,000 SF on floor 4 → `to.floor === 3`.
- `'ranks by smallest mover, then destination excess, then freed excess, then higher freed floor, and returns at most 3'`: four floors each with a blocker of 1,000, 1,500, 2,000 and 2,500 SF → three options, movers 1,000, 1,500, 2,000 in that order.
- `'a destination on the mover's own floor is allowed'`.

- [ ] **Step 3: Implement** `MoveOption` in `types.ts`, `MAX_MOVE_OPTIONS` in `constants.ts`, and the three functions in `makeRoom.ts`.

The approach the signatures do not fix:

1. If `findFits(b, req, D, today)` is not empty, return `[]`.
2. A mover is a leasable suite whose status on `D` is occupied or expiring, with `lease.end !== null` and `lease.start < D`.
3. For each mover, take the building with that suite's `leases` set to `[]` and call `findFits`; the first candidate is the provisional freed block (every candidate there contains the mover's suite, because nothing fitted before).
4. The destination is the suite with `statusAt` `vacant` and `overlay: 'none'`, `kind: 'leasable'`, `areaSf >= mover areaSf`, not in the provisional block, with the smallest area, ties to the higher floor. No destination: no option.
5. Build the option, apply `moveChanges` with `applyScenario`, and call `findFits` on the result. Keep the option only if the scenario applies and a candidate with the provisional key is returned; that candidate is `freed`.
6. Sort by `from.areaSf` ascending, `to.areaSf - from.areaSf` ascending, `freed.excessSf` ascending, `freed.floor` descending; take `MAX_MOVE_OPTIONS`.

```ts
export const FLIGHT_MS = 1600
export const FLIGHT_OUT = 9 // how far forward of its slot a block travels: more than a suite's depth (8.2), so it clears the facade
/** The flying block at progress k in [0, 1]: out of the facade, across to the destination, in. */
export function flightAt(from: Box, to: Box, k: number): Box
```

- [ ] **Step 1: Write the failing tests** in `moveFlight.test.ts`, with `from = { x: 4, y: 5, z: 0, w: 2, h: 0.87, d: 8.2 }` and `to = { x: -3, y: 4, z: 0, w: 3.5, h: 0.87, d: 8.2 }`:

```ts
it('starts as the source box and ends as the destination box', () => {
  expect(flightAt(from, to, 0)).toEqual(from)
  expect(flightAt(from, to, 1)).toEqual(to)
})
it('is clear of the facade for the whole crossing', () => {
  for (const k of [0.25, 0.5, 0.75]) expect(flightAt(from, to, k).z).toBeCloseTo(FLIGHT_OUT)
})
it('does not move sideways or change size before it is clear, nor after it is back in line', () => {
  expect(flightAt(from, to, 0.2)).toMatchObject({ x: 4, y: 5, w: 2 })
  expect(flightAt(from, to, 0.8)).toMatchObject({ x: -3, y: 4, w: 3.5 })
})
it('is half-way across at the mid-point', () => {
  expect(flightAt(from, to, 0.5)).toMatchObject({ x: 0.5, y: 4.5, w: 2.75 })
})
it('clamps k outside [0, 1]', () => {
  expect(flightAt(from, to, -1)).toEqual(from)
  expect(flightAt(from, to, 2)).toEqual(to)
})
```

- [ ] **Step 5: Implement `MoveFlight` and wire it in.**

- `MoveFlight` finds the `out` and `in` suites in the model and their boxes in the layout. If either is missing (floor view, or no preview), or reduced motion is on, it renders nothing.
- A new `out`/`in` pair starts a flight: one extra mesh (`shapes.box`, coloured with the destination suite's fill and side colours) positioned and scaled by `flightAt` each frame for `FLIGHT_MS`, calling `invalidate()` every frame while it runs, because rendering is on demand. - While the flight runs, the destination suite's box, its edges and its label are hidden; they appear when the block lands. The freed block's ring and rank badge need no change: they come from the model.
- When the preview ends mid-flight, the mesh goes and the destination is shown at once.
